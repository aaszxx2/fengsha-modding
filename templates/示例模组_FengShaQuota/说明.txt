================================================================================
  《烽沙》辎重配额  FengShaQuota  v1.0
  纯 UE4SS Lua 模组 —— 不修改游戏文件，不生成 / 销毁 / 搬运任何资源
================================================================================

一、这个模组解决什么
--------------------------------------------------------------------------------
  辎重库的库存被单一物资占满 → 别的物资送不进来 → 运输路线反复空跑。

  它让你给每座辎重库的每种物资设一个「目标库存」，并清楚看到：
  当前多少 / 目标多少 / 还差多少 / 是否已达标 / 是否禁止存入。

  它不会凭空生成或销毁资源，也不改产出。

二、快捷键
--------------------------------------------------------------------------------
  Ctrl+Q            开关配额面板
  Ctrl+Shift+Q      切换辎重库（按离你远近排序）
  Ctrl+Shift+W      切换物资（只列「有库存」或「已设配额」的）
  Ctrl+Shift+G      切换视图（按库 / 按物资 / 只看异常）
  Ctrl+Shift+E      目标 +步长（默认 +50）
  Ctrl+Shift+D      目标 -步长（减到 0 且无上限时自动恢复原版）
  Ctrl+Shift+F      禁止存入 / 取消
  Ctrl+Shift+C      把当前库的配额复制到「下一座」辎重库
  Ctrl+Shift+T      套用模板（每次按循环：均衡→粮食优先→建造储备→备战储备）
  Ctrl+Shift+X      重置当前库为游戏默认（同时恢复容量）
  Ctrl+Shift+V      诊断（写 dumps\diag_*.txt）

  面板里 ▶ 是当前选中行；改动会立刻写盘，重进存档仍在。

三、三种状态（每座库 · 每种物资独立设置）
--------------------------------------------------------------------------------
  不限量（默认）  不设配额 → 完全按游戏原规则
  目标库存        「希望存到多少」。达到后不再往这里补这种货；超出的部分保留不动
  禁止存入        不再把这种货运进来；已有库存不处理

  另有可选「库存上限」：与目标独立。
    · 只有目标：按目标停止补货
    · 只有上限：运到上限为止
    · 两者都有：以较低者为准；若上限 < 目标，面板会标「冲突」
    · 都没有：游戏原版行为

四、三种执行模式（config.txt 的 EnforceMode）
--------------------------------------------------------------------------------
  off        只读。面板、缺口、提醒、复制全部可用，但绝不改游戏状态。
             ← 不确定时先用这个

  capacity   容量闸门（默认）。
             当某座库「所有设了配额的物资都已达标」时，把这座库的容量压到
             「当前库存总量」，游戏自己的「仓库已满」逻辑就会拒绝再送入。
             库存因消耗下降到目标以下时，容量自动恢复原值。
             · 只用 SetCapacity(int32)，BlueprintCallable，逆向已确认存在
             · 永远不低于当前库存（不会导致物品丢失）
             · 容量不是 SaveGame 字段，退出游戏即还原，不会污染存档
             · 代价：整库级闸门，不是逐物品精确闸门（见「已知限制」）

  native     写游戏原生的「每物品上限」StorageMaxItems（实验性）。
             这条路径若可用，就是逐物品精确的。首次请先按 Ctrl+Shift+V 自检，
             看日志里 StorageMaxItems / RemoteDemandEntries 是否「可读」，
             再决定要不要切到 native。

五、首次使用步骤（建议照这个顺序）
--------------------------------------------------------------------------------
  1) 进存档，按 Ctrl+Q 看面板能不能列出你的辎重库
     · 列不出来 → 按 Ctrl+Shift+V，把 dumps\diag_*.txt 发我
  2) 先保持 EnforceMode = capacity，给一座库设两三个目标试试
  3) 观察面板：达标后该库应显示「配额全达标」，并且不再进新货
  4) 想更精细再切 native（先自检）

六、数据文件
--------------------------------------------------------------------------------
  data\quota.txt          你的配额（纯文本，可手工编辑 / 备份 / 分享）
  dumps\diag_*.txt        诊断输出
  config_items.txt        物资 ID → 中文名（逆向生成，勿手改）
  config.txt              配置

  quota.txt 格式（一行一条，TAB 分隔）：
    S  <库key>  <名字>  <x> <y> <z> <基准容量>
    Q  <库key>  <物资ID> <mode:target|block|unlimited> <目标> <上限>
  删掉某行 = 取消该条配额。整个文件删掉 = 全部恢复默认。

  注意：配额按「库的 Actor 名」匹配。同一张地图的不同存档会共用一份配额
  （这对「一套城市方案复用到新档」反而方便）；换地图则各自独立。

七、已知限制（v1.0 如实说明）
--------------------------------------------------------------------------------
  1. capacity 模式是「整库闸门」：
     只要这座库还有一项物资没到目标，容量就是全开，别的物资仍可能大量涌入。
     逐物品精确拦截需要 native 模式，或改 C++（本模组不做）。
  2. native 模式依赖从 Lua 写 USTRUCT 数组。TArray 里没有该物品的条目时，
     无法从 Lua 追加（会在日志里明说）。这种情况先用游戏自带的
     「供应/需求」面板给该物品建一条，再用模组调数值。
  3. 不接管运输路线：路线目的地达标时只提示，不会删除或改写你的路线。
  4. 不处理超额库存：目标调低后多出来的货留在库里，不会被搬走或卖掉。
  5. 敌方辎重库默认不计入（IncludeEnemy = false）。

八、需要实测的 4 处（出问题按 Ctrl+Shift+V 把 diag 发我）
--------------------------------------------------------------------------------
  1. 面板能否列出辎重库
     判据：日志 "扫描: N 座辎重库" 且 N>0
     若为 0 → 可能是 ConfigID 变了，或组件名不是 WarehouseStorageComponent
  2. 库存读取走的是哪条路
     判据：diag 里「库存来源=TotalItemNumList」为最佳；若是 GetItemNum 也能用但更慢
  3. SetCapacity 是否真的挡住进货
     判据：设一个小目标（如 50）装满后，看是否还有民夫往里送
     日志 Verbose=true 时能看到「容量闸门 ... → N」
  4. native 模式能否写入
     判据：diag 里 StorageMaxItems「可读」+ Items 条目数 > 0
     若不可读，native 模式不可用，请继续用 capacity

九、安全说明
--------------------------------------------------------------------------------
  · 不改游戏文件、不改 pak、不改存档结构
  · 不生成 / 销毁 / 出售 / 搬运任何资源
  · 容量闸门永远 >= 当前库存，最坏情况只是「暂时不进货」
  · 所有改动可用 Ctrl+Shift+X 一键恢复，或直接删 data\quota.txt
  · 建议首次使用前备份存档（%LOCALAPPDATA%\MOProject\Saved\SaveGames）

十、卡加载 / 卡顿怎么排错（2026-10-17 补）
--------------------------------------------------------------------------------
  v1.0 第一版有两个隐患，已修：

  ① 加载时用 os.execute 调 cmd.exe 建目录
     实测两次调用之间卡了 664ms（游戏线程被阻塞）。已改成纯文件探测，
     目录由安装脚本创建，模组不再 spawn 任何进程。

  ② 默认遍历 TotalItemNumList.Items（TArray<USTRUCT>）
     「读容器」在本作里是已知的崩溃/卡死路径。现在默认 ReadMode = getter，
     只用 GetItemNum() 逐个问（只读 int32）；array 路径要手动打开。

  另外：EnforceMode 默认改成 off（只读），并且 off + 面板没开时**完全不扫描**。
  也就是说，默认状态下这个模组对帧率零开销 —— 按 Ctrl+Q 才会干活。

  还是卡的话，按这个顺序二分（每步进游戏看一次）：

    bash E:/fs_mod/scripts/mod_toggle.sh list            # 看当前开关
    bash E:/fs_mod/scripts/mod_toggle.sh safe            # 关掉所有第三方 mod
    #  → 能进：说明是某个 mod 的问题，继续下一步
    #  → 还卡：不是 mod 的问题，去查存档 / 校验游戏文件
    bash E:/fs_mod/scripts/mod_toggle.sh restore         # 恢复
    bash E:/fs_mod/scripts/mod_toggle.sh off FengShaQoL  # 单独关 FengShaQoL 再试

  注意：FengShaQoL 是靠目录里的 enabled.txt 启动的，改 mods.txt 关不掉它，
  必须用上面的脚本（它会同时处理 enabled.txt）。

  第二个嫌疑是 mod 的 pak（Content\Paks\pakchunk0-Windows_P.*，32MB）。
  它是未签名包，本作很可能根本不挂载，但会参与启动扫描。排除方法：
    mkdir -p E:/fs_mod/backup_paks
    move "D:/STEAM/steamapps/common/mo/MOProject/Content/Paks/pakchunk0-Windows_P.*" E:/fs_mod/backup_paks/

  日志：Mods\FengShaQuota\dumps\diag_*.txt（Ctrl+Shift+V 生成）
        UE4SS.log（过滤 [FengShaQuota]）

十一、画面卡顿（2026-10-17 二次修）
--------------------------------------------------------------------------------
  按 Ctrl+Q 后画面卡一下 / 周期性掉帧，原因有四个，都已处理：

  ① 每次扫描都调 FindFirstOf("BuildingSubsystem")
     UE4SS 的 FindFirstOf 要遍历整个 GUObjectArray（几十万对象），
     这是最大的单点开销。→ 已改成缓存指针，只在失效时重查。

  ② 每轮先建「玩家建筑名字集合」
     旧写法对每座建筑做 IsValid + GetName（几百上千次 UE 调用），
     然后再遍历一遍全部建筑。→ 已改成直接迭代 AllPlayerBuildings，
     不再靠名字匹配，调用次数直接砍掉一半以上。

  ③ 按 Ctrl+Q 时同步跑完整个扫描
     按键回调里跑完整扫描 = 按键瞬间卡住。→ 已改成先画面板、
     扫描丢到下一个 tick 做（面板会先显示「扫描中…」）。

  ④ 面板每 3 秒无条件重设一次文本
     UMG 重排有成本。→ 内容没变就不 SetText。

  另外：单轮扫描 >80ms 会自动把间隔翻倍（最长 6s）并写日志，
  所以如果这台机器确实重，它会自己降频，不会持续拖帧。

  怎么确认是不是模组的问题：
    看 UE4SS.log 里这条（只会出现一次）
      [FengShaQuota] 首次扫描完成：N 座辎重库，库存来源=GetItemNum，耗时 X ms
    X < 50   → 模组很轻，卡顿另有原因
    X > 150  → 告诉我，我改成「每帧只处理一部分建筑」的增量扫描

  ★ 还有一个很容易被忽略的：UE4SS 的 Debugging Tools 控制台窗口
    （就是带 Live View / Watches / Lua Debugger 那个）。
    它开着会持续刷新日志列表，本身就有明显帧率代价。
    平时玩请把它关掉，只在排错时开。

十三、面板显示「建筑总数 0」（2026-10-17 四次修）
--------------------------------------------------------------------------------
  原因是我自己的 bug：`local arr` 被声明了两次，第二行把选好的数组覆盖成了
  `AllBuildings`，而当它读不到时就变成 nil，循环一次都没跑 → 总数 0。

  已修，并且顺手加了两件事：

  1) 枚举路径改成四级兜底，一条不通就换下一条
       ① BuildingSubsystem.AllPlayerBuildings
       ② BuildingSubsystem.AllBuildings
       ③ FindAllOf("MOBuildingBase")        ← 完全不依赖子系统
       ④ FindAllOf("InteractiveActorBase")
     面板会显示实际用的是哪一条（「来源=...」）。

  2) 面板现在会写明 BuildingSubsystem 是 OK 还是找不到，
     读不到建筑列表时会直接提示「把 diag 发我」。

  另外 FindFirstOf / FindAllOf 都是全对象扫描，很贵：
    · 找不到子系统时 30 秒内不再重试（原来 3 秒，每 3 秒卡一下）
    · FindAllOf 的结果缓存 10 秒

  按 Ctrl+Shift+V 生成的 diag 里现在有一段「建筑枚举路径探测」，
  会逐条列出每条路径读到多少个，一眼就能定位是哪一环断了。

十五、物流模式（2026-10-18 继续逆）
--------------------------------------------------------------------------------
  辎重库/粮仓（模块化那两栋）带一个物流站组件 BuildingLogisticsStationV4，
  它只有两个属性：LogisticsMode + ReceiveSlotTag。

  LogisticsMode 的取值（从 exe 里挖出来的完整枚举）：
      SendOnly      只发货
      ReceiveOnly   只收货     ← 辎重库/粮仓默认
      Both          既发又收

  ★ 没有「完全不收不发」这个值。所以「禁止存入」不能靠改模式实现：
    改成 SendOnly 虽然不再收货，但会开始往外发货（有路线时会运走东西），
    这违反「不自动搬走库存」的原则。

  因此 v1 仍然用容量闸门做整库停货；LogisticsMode 只读、只显示，不写。
  面板明细行现在会显示「物流=ReceiveOnly(只收货)」。

  各仓储建筑默认容量（BP 里写死的值）：
      辎重库(模块化) 1500   粮仓(模块化) 1500
      辎重库(旧)     2000   粮仓(旧)     2000
      军械库         4000   货栈          500

  注意：只有模块化辎重库/粮仓有物流组件；军械库和旧版 Storehouse/Granary 没有，
  它们的进出货走别的路径。

十六、原生逐物品写入已实现（2026-10-18 收尾）
--------------------------------------------------------------------------------
  现在有两个「逐物品」的原生字段可以写：

    StorageMaxItems        FMOItemNumList  { Items=[{ItemType, ItemNum}] }      → 库存上限
    RemoteDemandEntries    TArray<{ ItemType, ItemNum, bEnabled }>             → 目标量 + 禁止存入

  写入逻辑（都带「写完回读校验」）：
    目标库存   → RemoteDemandEntries[物品].ItemNum = 目标; bEnabled = true
    禁止存入   → RemoteDemandEntries[物品].ItemNum = 0;    bEnabled = false
    库存上限   → StorageMaxItems[物品].ItemNum = 上限

  打开方式（config.txt）：
    NativeMirror = true        # 与容量闸门并存，只写上面两个字段
    EnforceMode  = native      # 只走原生字段，不用容量闸门

  ★ 硬限制：TArray 不能从 Lua 追加元素。
    如果某个物品在游戏里从来没配过「需求」，数组里就没有它的条目，
    写入会返回「该物品无需求条目」而不是静默失败。
    解决办法：先在游戏自带的「供应/需求」面板给这个物品加一条，再用模组调数值。

  ★ 先用 Ctrl+Shift+V 自检
    diag 里新增「原生字段写回自检」：把每个数组第一条的原值写回去再读回来，
    显示「可写 ✔ / 只读 ✘」，并打印条目数。
    - 两个都「可写」→ 可以开 NativeMirror
    - 有「不可读」→ 该字段在这版引擎里没暴露，native 模式不可用，继续用容量闸门

十七、基准容量改用数据表（2026-10-25）
--------------------------------------------------------------------------------
  逆向出真实容量曲线后（辎重库/粮仓：LV1 1500 → LV2 2500 → LV3 4000），
  发现原来的「靠容量变大来推断基准」有风险：

    封口后容量被压到 240，此时建筑升级。
    如果游戏是「在当前值上加增量」，推断会把 1240 当成新基准 → 永久损失容量。

  已改成数据驱动：
    · 新增 config_capacities.txt（ConfigID → 基准容量，取自 BP 的 WarehouseStorage.Capacity）
    · 有表值就以表为准，没有才退回旧推断
    · 同时记录 store.cfg，检测到建筑升级会打日志并清 lastSet

  顺带明确一条行为：**配额为空时容量闸门不动作**。
  所以清空配额不会恢复容量，想恢复得留一个未达标的目标。
